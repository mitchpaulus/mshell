Call Options: .{ … } word

A way to attach named settings to a single call, without touching the stack. Nothing changes for programs that don't use it.

01

The problem

Some functions have one or two essential inputs and several settings that rarely change. Today the settings go on the stack as a required dictionary:

`myzip.zip` `out` {} zipExtract
`myzip.zip` `out` { "overwrite": true } zipExtract

That has three costs:

  1. Every call pays for the rare case. Callers write {} every time, and each call allocates a dict.
  2. Adding a setting can break callers. If a function had no settings before, adding the dict changes its stack effect.
  3. Misspelled keys pass. Shape types accept extra keys, so this type-checks cleanly today:
`a.zip` `out` { "overwrite": true, "overwrit": 1 } zipExtract   # --type-check-only: rc=0
Goal

A word keeps a fixed stack effect for its required inputs. Callers can optionally attach named settings that never touch the stack.

02

Is this the right approach?

Yes, with the constraints in the next section. I looked for something more fundamental. Here are the alternatives:

ApproachWhy not
Required dict on the stack (today)Every call pays for {}, misspelled keys pass, and adding settings to a function that had none is a breaking change.
Two names per function (Factor-style foo / foo*)No new syntax, but it doubles the builtins, does nothing for user definitions, and still needs a dict.
Builder objects (like command lists with > * ;)This works for commands because commands are values. Making every function a value you configure and then run is too heavy.
Settings scoped to a block: {…} (body) withOptionsSettings leak into every nested call. Hard to type. Bad for threads.
% item word (codex branch)The same core idea. See section 09 for the differences.
The primitive underneath

A call to one word can carry a read-only set of named values. That set lives in the call's frame, not on the stack.

Syntax, defaults, and typing all build on this. I don't see a simpler primitive that gives no cost to programs that don't use it, compile-time typo checking, and thread safety all at once.

03

Rules I'd keep fixed

  1. Options never change the stack effect. Not the number of inputs or outputs, and not their types. If a setting would change what comes back, that is a different function. This keeps the type checker simple.
  2. Options attach to exactly one word, chosen by the parser. .{…} must be immediately followed by a word. Nothing waits in interpreter-wide state for "the next call".
  3. The called word can't modify what it receives. It never gets an MShellDict that shares memory with a constant built at parse time.
  4. Required inputs stay on the stack. .{ } is only for things with a sensible default. httpGet's url stays on the stack.
  5. Unknown keys are an error, both in the type checker and at runtime.
04

Syntax

Call site

optionCall : ".{" dictEntries "}" LITERAL
`myzip.zip` zipExtract
`myzip.zip` .{ "overwrite": true, "destDir": `otherDir` } zipExtract
  • .{ is one token only when there is no space between . and {. Today it lexes as the literal . followed by a dict. I found no uses of that in lib/ or tests/. A lone . ([ls .]) is unaffected.
  • After } must come a LITERAL token (a function name), not a quote, variable, or number. Anything else is a parse error.
  • Values are ordinary expressions that each push exactly one value, as in dict literals: .{ "destDir": @out }, .{ "maxBytes": 10 1024 * 1024 * }.
  • Keys are always written out. They can't be computed.
Breaking change inside command lists

The meaning of [foo .{"a": 1}] changes. I think that's acceptable, but it needs a CHANGELOG note.

Declaring options on a definition

A definition declares its options once, with types and defaults. This is the "implicit default dictionary" the body reads from. I'd reuse the shape syntax and add = value for defaults:

def extract (path -- ) .{ overwrite: bool = false, destDir?: path, strip: int = 0 }
    ...
end

name: T = literal

The key has a default. Reading it always gives a T.

name?: T

No default. Reading it gives Maybe[T]. This covers defaults that depend on other inputs, like "destDir defaults to the zip's own directory".

  • Default values must be fixed literals, with the same rules as definition metadata.
  • The declaration goes after the signature. Inside the parens it would look like a stack input, which it isn't.
  • Why not infer types from the default values (.{ "overwrite": false })? That can't express "no default" or a union type, and both come up right away (destDir).

Reading options in the body

"overwrite" opt   # bool, from the caller or the default
"destDir" opt     # Maybe[path]

The type checker requires the key to be a string literal that the definition declares, so each key can be resolved to a slot index ahead of time. .name can't be the shorthand, because literals like .gitignore are common inside command lists.

Getting all the options at once (to loop over or pass along) would be opts. It builds a new dict. The author chooses to pay that cost.

05

Runtime design

No cost when unused

  • Lexer: one extra check when a token starts with ..
  • Parser: a new node, *MShellParseOptionCall, appears only when .{ does. Other programs produce the same parse trees as today.
  • Evaluator: a new case in the dispatch on parse-item type. It only runs for the new node.
  • EvaluationFrame gets one pointer, Opts *CallOptions, which is nil for normal calls. callDefinition already allocates a new context and a variables map for every call, so this won't show up in measurements.
  • evaluateToken (the builtins) gets one extra *CallOptions argument, nil at every existing call site.

No dictionary is allocated whether or not options are used.

Data structure

Not an MShellDict. Option sets are small (usually 1–6 keys), so a slice is faster and smaller than a map.

// Built at parse time, shared, never modified.
type OptionKeys struct {
    Names []string        // sorted
}

type CallOptions struct {
    Keys   *OptionKeys
    Values []MShellObject // same order as Keys.Names
}

To look up a key, scan Names, or use a slot index the type checker worked out ahead of time.

Tier 1 · no per-call allocation

Every value is a simple literal

str, int, float, bool, path, datetime, none. The parser builds one CallOptions for the call site, and every call reuses that pointer.

Tier 2 · one small allocation

Any value is computed

@var, an expression, or a list/dict literal. Each call allocates one slice of length n. Single-token values are looked up directly. Only multi-token values go through the dict-literal frame machinery.

List and dict literals always go in tier 2. Each call builds a new list, as the language does today. That stops one call from appending to a list that the next call would see.

How the callee reads a value

"k" optissued in the definition body
→
1. Call-site optionsframe.Opts: if k is present, return it
→
2. Declared defaultstored with the definition when parsed. Returns none for ?: keys

Nothing is merged or copied. Both sources are shared across calls, and later across threads, so they are only ever read. opt returns the values themselves, and opts returns a copy.

Builtins: today the option parsers (parseZipExtractOptions and others) read keys through helpers like boolOption(dict, …). Change those helpers to take a small interface that both *MShellDict and *CallOptions implement, so each builtin's option parsing is written once. A later optimization: a tier-1 call site could cache the builtin's parsed Go options struct on the parse node.

Easy to get wrong

Tail callscallDefinition reuses the frame for a tail call. It must set frame.Opts to the new call's options, or nil. Otherwise the caller's options leak into the definition it tail-calls.
Nested callsIn .{ } a where a calls b, b sees no options. Options are never inherited. A wrapper passes them on explicitly: .{ overwrite: "overwrite" opt } zipExtract.
if / loop / match framesThese run inside a definition and must still find the definition's options. Copying the pointer into child frames is simplest and allocates nothing.
Unknown keys at runtimeWithout --check-types, check the keys when the call is made, against the definition's declared keys or the builtin's list of accepted keys. This only runs when options are used.
Existing parsersparseZipExtractOptions accepts "overwrit" without complaint. The new path should reject it.
06

Parallel execution

The design needs no locks:

  • Call options live on the evaluation frame. Each thread will have its own EvalState and frames.
  • The only shared data is built at parse time: key tables, tier-1 CallOptions, and declared defaults. These hold simple values and are only ever read, so any number of threads can use them.
  • Tier-2 values are created by the calling thread in a new slice that belongs to that one call.
  • List and dict literals are rebuilt on every call, so no list is shared between threads.
  • Nothing is added to EvalState. Its CallStack and LoopDepth will need to become per-thread anyway.
Unrelated, but noticed

lookupDefinition rebuilds defIndex the first time it's needed. Once there are threads, that's a data race.

07

Typing

Declarations

  • Builtins register an options shape next to their signature, e.g. r.regOptions("zipExtract", "{overwrite?: bool, skipExisting?: bool, stripComponents?: int, …}").
  • Definitions get their options shape from the .{ … } declaration.
  • Using .{ } on a word that declares no options is an error: "zipList does not take options".

Call site

  • The .{} literal is checked against the word's options shape as a closed shape, which rejects unknown keys (dicts on the stack accept them today). This is the typo check.
  • Each value is checked against its field's type.
  • The call's stack effect is the word's normal signature. The checker handles .{…} word as "check the options, then check word".
  • A word with several overloaded signatures has one options shape for all of them. Options never choose an overload.

Inside the body

ExpressionType
"k" opt, declared k: T = vT
"k" opt, declared k?: TMaybe[T]
"k" opt, key not declared or not a literalerror
optsthe declared shape, with fields that have defaults always present

Quotations

.{ } x, or options on any quotation value, is not supported in v1. A quotation type (a -- b) has nowhere to record options, and adding that would affect every quotation type. .{ … } sortBy is fine, because the options belong to sortBy, not to the quotation it runs.

08

Migration

Moving the existing builtins that take an options dict (zipExtract, zipExtractEntry, tar*, numFmt, …) to .{ } changes their stack effects, which breaks callers.

Recommended for zip/tar

1. Change them in one release

Add a CHANGELOG entry. The number of inputs changes, so the type checker points to every call site.

2. Keep old forms, add new names

Brings back the two-names-per-function problem.

Your example also makes destDir an option, so zipExtract would become (path -- ). Each of the other functions needs its own decision.

09

Compared with the % proposal

The same core: the parser attaches the options to one word, and nothing is stored in interpreter-wide state.

% (codex).{ (this)
Right sidedict literal or @vardict literal only
Defaultswritten in the body: @opt :k 5 maybedeclared once, read with "k" opt
Typo checkingnot possible for @varclosed-shape check
Lexer impactreserves % entirelyonly .{ with no space
Built at parse timenoyes, when all values are simple literals

The real cost of .{ is losing @var, the ability to reuse a saved set of options. If we need it later, .@var word could be added, with the key check done at runtime for that form. I'd leave it out of v1.

Open questions for you

  3. Bare keys at the call site. Allow .{ overwrite: true } to match type-expression syntax?
