Printable ASCII is computed. Complete non-ASCII grapheme clusters are measured once, cached for the terminal session, and never guessed. Layout remains pure because all terminal I/O happens before layout begins.

01

The contract is intentionally small

Width is not a Unicode property owned by mshell. It is an observed property of the terminal currently in front of mshell.

The previous design attempted to classify terminals with three parameters and then predict every cluster from that classification. That is attractive but not correct: partial clusterers, Unicode-version drift, configuration, and individual terminal quirks do not form eight clean equivalence classes. This design removes the classification problem.

Assumption A

A complete, self-contained printable grapheme cluster occupies one or two cells on supported terminals.

Assumption B

Printable ASCII occupies one cell per byte. Newline and renderer controls are handled explicitly.

Assumption C

Supported terminals preserve accepted grapheme boundaries, and an accepted cluster has the same cell advance in the probe and in surrounding text throughout one terminal-width cache epoch.

Assumption D

The terminal answers a standard cursor-position request when exact non-ASCII display is enabled.

These are runtime contracts, not universal claims about Unicode or every historical terminal. Interactive editing and width probing require a terminal at least four columns wide. Invalid cursor reports and unsupported observed advances have a defined fallback. CPR reports cursor position, not screen contents; it cannot prove visual isolation or context-independent width. Those remain supported-terminal assumptions, not properties established by a successful probe.

Terminology

CSI 6 n, commonly written ESC[6n, is a Device Status Report request. The terminal answers with a Cursor Position Report, CSI row ; column R. This document calls the exchange DSR/CPR. SGR is reserved for styling such as color and bold; it is unrelated to measurement.

Explicit non-goals

  • No terminal identity database.
  • No cluster-versus-codepoint model selection.
  • No Mode 2027 inference ladder.
  • No use of the width returned by uniseg.FirstGraphemeCluster….
  • No persistent width cache whose correctness depends on identifying a terminal across sessions.
  • No query during ordinary ASCII typing, cursor motion, or repaint.

Resolve first, then lay out

The first boundary is a classification of the complete command buffer. A command containing only printable ASCII bypasses atomization and width resolution and is laid out directly from its source bytes. Every other command takes the general path, where width resolution is impure and may talk to the terminal before layout accepts resolved display atoms. Both layout paths perform no I/O. Rendering accepts only a completed layout.

Defined offset and cell types prevent the original bug class: adding a byte or rune index directly to a terminal column. The cursor is always a byte offset at a grapheme boundary.

AtomAscii and AtomGrapheme use a source slice as Text. AtomControl uses generated safe display text, and a placeholder uses one fixed printable ASCII character. Both retain the original source range; neither emits those source bytes raw.

Reuse is part of the interface

Resolution and layout accept destination slices owned by the editor state and reuse their backing arrays across generations. Cache keys are cloned only when inserted into the session cache, so a short measured cluster cannot retain an entire pasted command buffer. The first implementation uses straightforward scalar loops; representation or scan optimizations require benchmark evidence.

The prompt is opaque

The prompt may contain SGR, OSC, arbitrary user code, or cursor movement. Do not parse it into the command layout. Print it, issue one fenced CPR, and treat the reported position as the editing region's origin. The layout input is therefore either (printable command source, cursor, origin column, terminal width) or (resolved command atoms, cursor, origin column, terminal width), never prompt + command.

If the prompt anchor query fails, emit a real newline and start the editing region at column one. That fallback changes presentation but preserves geometry.

Printable-ASCII layout bypass

If every byte in the complete command buffer is in the printable ASCII range 0x20 through 0x7e, bypass atomization and width resolution entirely. The ASCII layout function consumes SourceText directly: every byte occupies one cell, every byte boundary is a valid wrapping and cursor boundary, and rows can refer directly to slices of the original command. The normal interactive command therefore needs one validation scan and no per-character atom construction.

A tab, newline, other control byte, DEL, or non-ASCII byte fails this classification and sends the complete command through the general atomizer. That path maps tab to ▸ (U+25B8 BLACK RIGHT-POINTING SMALL TRIANGLE), represents other controls safely, and segments Unicode graphemes. Its display atoms are indivisible; there is no exceptional atom type that layout may sometimes split. Do not retain an independently scanned ASCII prefix when classification fails: a combining codepoint may join its final ASCII base, and the common path should not build general-path state speculatively.

Uniseg has one job

Use uniseg to identify extended grapheme-cluster boundaries and valid cursor gaps. Ignore every width it reports. After every edit, derive boundaries again; edits can change segmentation, particularly for regional indicators and joiner sequences.

Candidate eligibility is a separate cached decision

Uniseg returns boundaries even for degenerate clusters such as a standalone combining accent. It does not return an independently-displayable flag. Before width lookup or measurement, segment "A" + candidate + "A" and require exactly three clusters whose bytes are "A", the unchanged candidate, and "A". These sentinels exist only in memory; they are not printed by the terminal probe.

For example, e + U+0301 remains one separate cluster and passes. A standalone U+0301 COMBINING ACUTE ACCENT joins the preceding sentinel and fails. This is a conservative eligibility policy under uniseg's segmentation rules, not proof of terminal rendering behavior.

CandidateEligibilityCache stores both acceptance and rejection by exact candidate bytes. A cached false value must be distinguished from a missing entry. Entries use cloned keys, preventing a small candidate from retaining an entire source buffer. The cache holds at most 4096 entries; empty candidates and candidates longer than 256 bytes are rejected without insertion. Once full, existing decisions remain usable and unseen candidates are rejected without repeating segmentation.

Eligibility lasts for the editor session and survives terminal width-cache epoch changes because it depends on the editor's segmentation rules. A measurement timeout does not change an accepted eligibility decision. resolveCachedWidths changes rejected atoms to one-cell placeholders immediately, retaining their source ranges; only eligible candidates proceed to width lookup or the miss list.

Exact cache keys

Cache by the exact UTF-8 bytes of the complete cluster. A measured family emoji says nothing about a different family emoji. A measured VS16 sequence says nothing about every sequence containing VS16. This refusal to generalize is what makes the cache an observation rather than another predictive model.

Why the two-cell bound matters

The one-or-two-cell contract removes the old oversized-cluster splitting design completely. A complete non-ASCII grapheme atom always fits on an empty row at the supported minimum of four terminal columns. It also turns measurement validation into a closed check: a result outside one or two is unsupported, not another layout case. 

func ResolveGeneralInto(dst []DisplayAtom, missDst []string, command SourceText,
    cache *WidthCache, eligibility *CandidateEligibilityCache) ([]DisplayAtom, []string) {
    atoms := segmentAtomsInto(dst, command)
    misses := resolveCachedWidths(missDst, command, atoms, cache, eligibility)
    return atoms, misses
}

Cache lifetime

The width cache lives in memory and normally spans prompts. It is tied to a width epoch: the period during which mshell owns and reasserts its terminal modes and assumes the terminal's width behavior is stable. Start a new epoch after terminal reattachment, resume when state cannot be trusted, or any explicit recalibration command. Resize alone does not change cluster width and does not clear the cache.

Do not write the cache to disk in the first implementation. Correct invalidation across terminal upgrades, tmux attachments, font changes, and configuration is harder than remeasuring the small set of clusters a user actually types.

04

Measure a batch in one transaction

Resolve every distinct cache miss in the newest editor state before layout. A paste containing repeated clusters measures each distinct byte string once. All probes are emitted in one buffered write and all replies are then collected by the normal terminal-input lexer.

Resolution is resource-bounded. Measure at most a fixed number of distinct misses in one editor generation and cap both cache entries and candidate byte length. Overflow candidates use the known-width placeholder; they are not allowed to create an unbounded query burst or cache from an adversarial paste. A first implementation can use conservative constants such as 256 probes per generation and 4096 cache entries.

server / msh
probe A + CPRprobe B + CPRprobe C + CPRwait
terminal
A replyB replyC reply

There is one CPR response per distinct unknown cluster, but the requests are not serialized. On SSH or ConPTY the batch can travel as roughly one additional transport round trip, independent of the number of misses in that batch. Ordinary cached or printable-ASCII edits pay no round trip.

Probe from a known cell

The renderer provides one owned scratch row outside the visible edit contents. Each probe clears pending wrap and moves to column one with CR, clears the scratch row, writes exactly one eligible candidate cluster, and requests CPR. There is no printed ASCII prefix. 

for cluster in misses:
    write(CR + EL + cluster + CPR)
    write(CR + EL)

// Column numbers are one-based.
measuredWidth = replyColumn - 1
require replyRow == scratchRow
require measuredWidth == 1 || measuredWidth == 2

Raw newlines, tabs, C0/C1 controls, and ESC never enter this protocol. The generated tab glyph ▸ goes through the same eligibility check and width resolution as other candidates. CPR observes cursor advance only; neither the eligibility check nor the probe can detect arbitrary visual changes or prove behavior with every possible neighbor.

Four columns is the absolute minimum supported terminal width for both interactive painting and width probing. Below four columns, do not paint interactive contents or issue width probes; continue accepting editing keys or report that the terminal is too narrow.

The four-column minimum avoids the three-column ambiguity: a two-cell candidate reports column three, while an unsupported three-cell candidate reports column four and is rejected. Supported one-or-two-cell candidates cannot leave pending wrap in the probe. CPR still does not expose pending-wrap state or prove arbitrary terminal behavior; the supported-terminal assumptions continue to apply.

parseCursorReport validates CPR syntax and positive coordinates up to the supported limit of 9999. widthFromCursorReport then requires the expected scratch row and accepts only reply column two (width one) or three (width two). It performs no I/O and makes no cache changes; the batch collector must establish reply ownership and decide whether measurements can be committed.

Scratch-row ownership

Do not use terminal save/restore-cursor state. Move relative to the renderer's known region, create or reuse a row immediately below the previous editing region, and account for a scroll if creating that row reaches the bottom of the screen. Clear the scratch row before leaving it. After replies are validated, repaint the editing region from its tracked origin.

The initial prompt can perform capability validation before showing editable text. Later cache misses temporarily leave the previous correct frame visible; mshell does not optimistically paint a layout with guessed widths.

Replies share the keyboard stream

While a batch is outstanding, the lexer routes exactly the expected number of valid CPR tokens to the resolver and queues ordinary input tokens. A generation number associates a requested layout with the editor state that requested it. If more input arrives before resolution completes and the complete batch validates, commit its measurements, discard the stale layout, apply queued input, and resolve the newest state. 

generation 41: measure ["❤️"]
keypress arrives: editor becomes generation 42
generation 41 reply: cache "❤️" = 2; do not render generation 41
generation 42: resolve remaining misses, layout once, render once

05

Two pure layout paths

Printable ASCII layout is direct byte and cell arithmetic. General layout begins only after every display atom has a known width, then uses integer arithmetic over indivisible atoms. Both functions are deterministic, allocation-conscious, and incapable of querying the terminal. 

func LayoutPrintableAsciiInto(
    dst       []LayoutRow,
    command   SourceText,
    cursor    ByteOffset,
    startCol  Cells,
    columns   Cells,
) LayoutResult

func LayoutAtomsInto(
    dst       []LayoutRow,
    atoms     []DisplayAtom,
    cursor    ByteOffset,
    startCol  Cells,
    columns   Cells,
) LayoutResult
  • The printable-ASCII path may wrap at any byte boundary because each source byte is exactly one cell.
  • Every general-path text atom is a complete grapheme cluster, printable ASCII byte, generated control representation, or placeholder with a resolved width.
  • No general-path atom is split across rows. With the supported-terminal contract and terminal width at least four, every first-implementation atom fits on an empty row.
  • The first row begins at the measured prompt column; subsequent soft-wrapped rows begin at column one.
  • Hard newlines are source atoms with explicit row semantics and zero printable width.
  • The cursor may land at any byte boundary on the printable-ASCII path and only at source grapheme boundaries on the general path; either maps to exactly one row and cell gap.
  • Every row width is at most the available terminal width.
  • For printable-ASCII input, both paths produce identical rows and cursor placement.

Soft wrap remains terminal-owned

The renderer does not insert CRLF at calculated soft-wrap boundaries. It streams the row contents and lets terminal autowrap create soft breaks, preserving selection rejoin and resize reflow. Hard newlines in the source remain hard breaks.

Filling the final column arms the terminal's hidden pending-wrap state. The layout records that state explicitly. When another row follows, printing its first real atom forces the wrap; CR cancels pending wrap when returning to the region origin.

Full-region repaint first

Start with a whole-region repaint assembled into one output buffer. Home to the known origin with relative movement, paint source slices and fixed placeholders with natural autowrap, erase renderer-owned leftovers, and park the cursor from the layout result. A later desired-versus-actual diff renderer can consume the same layout without changing width resolution.

Styling is orthogonal

Syntax highlighting produces style spans over source byte offsets. The painter intersects those spans with layout atoms and emits SGR only while painting. SGR bytes have no width and never appear in SourceText, segmentation, the width cache, or layout arithmetic.

The more detailed paint-domain vocabulary and region-rendering figures remain in render-pipeline.html. Where that document refers to predictive cluster/codepoint width parameters, this document now supersedes it.

Correct failure beats plausible drift

Atomic batch rejection

Stage observations outside the width cache until every expected reply has arrived and the complete batch has validated. A malformed reply, unexpected row, unsupported observed width, timeout, or terminal I/O failure rejects all measurements from that batch, including individually valid observations. Previously cached widths and all candidate eligibility decisions remain intact. Recover the owned terminal region and use placeholders for widths that remain unknown. An editor generation change alone is not a measurement failure: commit a valid batch but discard its stale layout.

Retry only after command submission

A failed width batch sets a per-command widthProbesBlocked flag. Subsequent edits continue using cached widths and placeholders without issuing new width probes. Clear the flag when the command is submitted and the editor begins a new prompt, allowing unknown widths needed by the next command to be measured again. Enter that merely inserts a newline into an unfinished command does not clear the flag. Neither cache is cleared by this reset, and failed measurements remain unknown rather than becoming permanently rejected eligibility entries.

There is no retry timer or cooldown. An outstanding query still needs a timeout, and recovery must account for late replies before any subsequent query, including prompt anchoring, can start. Clearing the flag permits another measurement attempt; it does not bypass query recovery. Eligibility rejection, resource limits, and insufficient terminal width skip candidates or probes without constituting a failed batch.

The placeholder changes display text but not source text. Submission still uses the original UTF-8 bytes. A placeholder atom retains the source start/end offsets of the cluster it represents, so cursor movement and editing remain structurally correct.

Raw controls are never painted

Raw terminal controls cannot be allowed into the paint stream. They remain in SourceText because editing and submission operate on the exact command. Resolution turns C0 controls and DEL into AtomControl values using two-cell ASCII caret notation: NUL is ^@, Ctrl-Z is ^Z, ESC is ^[, and DEL is ^?. Tab is the exception: it paints as ▸, whose exact one-or-two-cell width is measured and cached for the terminal epoch. C1 controls use a fixed printable ASCII fallback in the first implementation; their source bytes are still preserved. Literal newlines are explicit hard-break atoms. The painter must never copy an AtomControl's source slice to the terminal device.

What correctness means here

  • mshell never calls a Unicode table's width estimate an observed terminal width.
  • Every painted non-ASCII cluster has either an exact cache entry from this terminal epoch or a known-width ASCII placeholder.
  • Every layout is computed from the same widths the painter will emit.
  • A failed or stale measurement can delay or degrade one frame, but cannot corrupt future row bookkeeping.
  • Terminal-specific behavior is contained in one resolver instead of leaking through layout and rendering.

Implementation order

  1. Replace width parameters with an injected exact width lookup in layout tests.
  2. Add the scalar printable-ASCII classifier and direct ASCII layout path.
  3. Introduce reusable DisplayAtom slices and whole-buffer general atomization for every input that fails printable-ASCII classification.
  4. Convert general layout to accept indivisible atoms and both layout paths to accept a measured prompt-origin column.
  5. Build the batch measurement protocol against a fake terminal and PTY tests.
  6. Add the session cache, generation handling, timeouts, and placeholder fallback.
  7. Swap the interactive renderer to region-relative repainting.
  8. Add terminal-mode lifecycle and platform backends without changing the width/layout interfaces.
  9. Run the real-terminal matrix and only then remove the old renderer.

Current implementation checkpoint

Pure ASCII and atom layout, segmentation, width-cache helpers, and placeholder resolution are implemented. Candidate eligibility is now cached and integrated into width resolution, with a test covering a standalone combining accent and an accent with its base. CPR parsing and conversion to a one-or-two-cell observation are implemented and tested for probes without an ASCII prefix. Session ownership of these caches, the batch collector, terminal probes, and integration with the interactive renderer remain to be implemented. Existing pure layout helpers still accept widths of two or more as mathematical inputs; that does not imply interactive support below four columns. Enforcing the four-column minimum at the editor and probe boundaries remains integration work.

08

Test the boundaries, not a model

Pure unit and property tests

  • Printable-ASCII classification accepts exactly bytes 0x20 through 0x7e; tab, newline, other controls, DEL, and every non-ASCII byte select the general path.
  • Direct printable-ASCII layout creates no display atoms and produces the same rows and cursor placement as the general atom path for printable-ASCII inputs.
  • Every C0 control and DEL retains its byte range, resolves to the correct safe representation, and can never place the raw control byte in ScreenBytes.
  • Tab paints as ▸; cache hit, exact measurement, timeout fallback, and one- versus two-cell observations all preserve its source offsets.
  • At a mixed ASCII/non-ASCII boundary, classify without constructing partial atoms and segment the complete buffer so combining marks can join the final ASCII base.
  • Segment every stress string and verify atoms tile source bytes exactly.
  • Inject arbitrary width maps containing only one and two; never call a terminal from layout tests.
  • For every grapheme-boundary cursor position and supported terminal width at least four, rows stay within bounds and the cursor lands on a valid cell gap. Pure layout tests may additionally exercise widths two and three.
  • Hard breaks, exact soft fills, early soft wraps, trailing newlines, and first-row prompt offsets retain explicit invariants.
  • Cache deduplication measures each exact cluster once per epoch.
  • Eligibility accepts an accent with its base and rejects a standalone accent; rejected atoms never enter the probe list and retain their source ranges.
  • Eligibility caches both true and false decisions, survives width-cache epoch changes, and rejects unseen candidates without segmentation when full.
  • Probe, cache-entry, and candidate-length limits always produce placeholders rather than unbounded work.
  • Editing that changes segmentation re-derives boundaries and does not reuse a cache entry for a different byte string.
  • Resolution and layout reuse caller-provided backing arrays without retaining stale atoms or rows.

Performance benchmarks

  • Benchmark short all-ASCII commands representative of interactive typing, not only large throughput inputs.
  • Benchmark mixed input whose first non-ASCII byte occurs near the beginning and near the end.
  • Benchmark large ASCII and Unicode pastes with allocation counts and bytes per operation reported.
  • Use the scalar printable-ASCII classifier as the baseline; compare word-at-a-time or SIMD validation against it before increasing complexity.
  • Keep the direct ASCII path allocation-free apart from caller-owned row capacity; optimize the general path independently when profiles justify it.

Protocol tests with a fake terminal

  • Several probes are written before any reply is required.
  • Replies populate the correct cache keys even when keypress tokens are interleaved.
  • Malformed reply, wrong row, unsupported observed width, timeout, and terminal I/O failure discard the entire batch, including otherwise valid observations; preexisting width and eligibility entries remain intact.
  • A failed batch blocks new width probes during subsequent edits of the same command; cached widths and placeholders remain usable.
  • Submitting a command and beginning the next prompt clears the probe block; inserting a multiline newline does not. Retry requires completed query recovery and uses no cooldown timer.
  • Late replies from a rejected batch cannot be mistaken for replies to a new batch or prompt-anchor query.
  • Probes contain no ASCII prefix; reply columns two and three resolve to widths one and two. Below four columns, neither interactive painting nor width probing is allowed. At four columns, an unsupported three-cell candidate reports column four and is rejected.
  • A stale generation retains valid measurements but never paints its stale layout.
  • The scratch row is cleared and terminal mode is restored on every exit path.

Real-terminal matrix

Run the existing tests/terminal_tests/width_report.py and the new DSR/CPR latency harness in each target environment. Then exercise the actual editor through a PTY with ASCII, combining text, CJK, VS15/VS16, flags, skin tones, keycaps, ZWJ sequences, paste, resize, tmux, SSH, ConPTY, and a terminal that ignores CPR.
