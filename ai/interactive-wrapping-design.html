Measure the unknown.

Printable ASCII is computed. Complete non-ASCII grapheme clusters are measured once, cached for the terminal session, and never guessed. Conservative space bounds and explicit hard wraps keep each cluster on one row, even on terminals that render its codepoints separately. Layout remains pure because all terminal I/O happens before layout begins.

01

The contract is intentionally small

Width is not a Unicode property owned by mshell. It is an observed property of the terminal currently in front of mshell.

The previous design attempted to classify terminals with three parameters and then predict every cluster from that classification. That is attractive but not correct: partial clusterers, Unicode-version drift, configuration, and individual terminal quirks do not form eight clean equivalence classes. This design removes the classification problem.

Assumption A

Ordinary text processing advances at most two cells per codepoint. For a candidate containing N codepoints, 2 × N bounds both its final advance and the furthest cursor advance while receiving any prefix, provided no wrapping occurs.

Assumption B

Printable ASCII occupies one cell per byte. Newline and renderer controls are handled explicitly.

Assumption C

An eligible cluster is self-contained and has the same final cell advance in the cleared probe row and in surrounding text when given sufficient space throughout one terminal-width cache epoch. The terminal may render its components separately; it need not use mshell's grapheme boundaries internally.

Assumption D

CPR support is required for interactive use. Every cursor-position request eventually receives a response in request order. Responses may be slow; the editor keeps reading without deadlines or timeouts.

These are runtime contracts, not universal claims about Unicode or every historical terminal. Interactive editing and width probing require a terminal at least four columns wide. Invalid cursor reports and unsupported observed advances have a defined fallback. CPR reports cursor position, not screen contents; it cannot prove visual isolation or context-independent width. Those remain supported-terminal assumptions, not properties established by a successful probe.

Editing and movement are always grapheme-based. Width is measured for the complete cluster and may exceed two cells. Probe and paint only when the conservative bound fits with a guard cell; otherwise hard-wrap before painting or use a placeholder if even an empty row is too small.

Here N is the count of Unicode codepoints in the display candidate, not its byte length or its measured width. A seven-codepoint cluster may measure eight cells on one terminal and two on another; both are accepted when the bound of fourteen cells can be accommodated. Movement crosses that entire cluster, and deletion removes all of its source bytes in either case. Explicit sizing protocols such as Kitty OSC 66 are not emitted for editable command text or probes. Source escape/control bytes are displayed safely rather than executed.

Terminology

CSI 6 n, commonly written ESC[6n, is a Device Status Report request. The terminal answers with a Cursor Position Report, CSI row ; column R. This document calls the exchange DSR/CPR. SGR is reserved for styling such as color and bold; it is unrelated to measurement.

Explicit non-goals

  • No terminal identity database.
  • No cluster-versus-codepoint model selection.
  • No per-codepoint or prefix-width probing and no attempt to infer component wrap boundaries from cursor advances.
  • No requirement to preserve terminal soft-wrap rejoining for conservatively wrapped clusters.
  • No Mode 2027 inference ladder.
  • No use of the width returned by uniseg.FirstGraphemeCluster….
  • No persistent width cache whose correctness depends on identifying a terminal across sessions.
  • No query during ordinary ASCII typing, cursor motion, or repaint.

The first boundary is a classification of the complete command buffer. A command containing only printable ASCII bypasses atomization and width resolution and is laid out directly from its source bytes. Every other command takes the general path, where width resolution is impure and may talk to the terminal before layout accepts resolved display atoms. Both layout paths perform no I/O. Rendering accepts only a completed layout.

Defined offset and cell types prevent the original bug class: adding a byte or rune index directly to a terminal column. The cursor is always a byte offset at a grapheme boundary. Arrow movement, word movement, selection/replacement, completion insertion, and all deletion paths must preserve or restore that invariant after resegmentation. Display fallback and terminal clustering behavior never introduce extra editing positions inside a source grapheme.

AtomAscii and AtomGrapheme use a source slice as Text. AtomControl uses generated safe display text, and a placeholder uses one fixed printable ASCII character. Both retain the original source range; neither emits those source bytes raw.

Reuse is part of the interface

Resolution and layout accept destination slices owned by the editor state and reuse their backing arrays across generations. Cache keys are cloned only when inserted into the session cache, so a short measured cluster cannot retain an entire pasted command buffer. The first implementation uses straightforward scalar loops; representation or scan optimizations require benchmark evidence.

The prompt is opaque

The prompt may contain SGR, OSC, arbitrary user code, or cursor movement. Do not parse it into the command layout. Print it, issue one fenced CPR, and treat the reported position as the editing region's origin. The layout input is therefore either (printable command source, cursor, origin column, terminal width) or (resolved command atoms, cursor, origin column, terminal width), never prompt + command.

Send one anchor request and queue ordinary input until its response arrives; do not send another request for each intervening keypress. On a malformed anchor response, emit CRLF and begin the editing region at column one, using region-relative bookkeeping rather than guessing an absolute row. Any subsequent scratch-row query must establish its actual row before probing. EOF or terminal I/O errors exit interactive mode through cleanup; silence alone is not an error or a fallback trigger.

Printable-ASCII layout bypass

If every byte in the complete command buffer is in the printable ASCII range 0x20 through 0x7e, bypass atomization and width resolution entirely. The ASCII layout function consumes SourceText directly: every byte occupies one cell, every byte boundary is a valid wrapping and cursor boundary, and rows can refer directly to slices of the original command. The normal interactive command therefore needs one validation scan and no per-character atom construction.

A tab, newline, other control byte, DEL, or non-ASCII byte fails this classification and sends the complete command through the general atomizer. That path maps tab to ▸ (U+25B8 BLACK RIGHT-POINTING SMALL TRIANGLE), represents other controls safely, and segments Unicode graphemes. Its display atoms are indivisible; there is no exceptional atom type that layout may sometimes split. Do not retain an independently scanned ASCII prefix when classification fails: a combining codepoint may join its final ASCII base, and the common path should not build general-path state speculatively.

Uniseg has one job

Use uniseg to identify extended grapheme-cluster boundaries and valid cursor gaps. Ignore every width it reports. After every edit, derive boundaries again; edits can change segmentation, particularly for regional indicators and joiner sequences.

Candidate eligibility is a separate cached decision

Uniseg returns boundaries even for degenerate clusters such as a standalone combining accent. It does not return an independently-displayable flag. Before width lookup or measurement, segment "A" + candidate + "A" and require exactly three clusters whose bytes are "A", the unchanged candidate, and "A". These sentinels exist only in memory; they are not printed by the terminal probe.

For example, e + U+0301 remains one separate cluster and passes. A standalone U+0301 COMBINING ACUTE ACCENT joins the preceding sentinel and fails. This is a conservative eligibility policy under uniseg's segmentation rules, not proof of terminal rendering behavior.

CandidateEligibilityCache stores both acceptance and rejection by exact candidate bytes. A cached false value must be distinguished from a missing entry. Entries use cloned keys, preventing a small candidate from retaining an entire source buffer. The cache holds at most 4096 entries; empty candidates and candidates longer than 256 bytes are rejected without insertion. Once full, existing decisions remain usable and unseen candidates are rejected without repeating segmentation.

Eligibility lasts for the editor session and survives terminal width-cache epoch changes because it depends on the editor's segmentation rules. A rejected measurement does not change an accepted eligibility decision. resolveCachedWidths changes rejected atoms to one-cell placeholders immediately, retaining their source ranges; only eligible candidates proceed to width lookup or the miss list.

Exact cache keys

Cache by the exact UTF-8 bytes of the complete cluster. A measured family emoji says nothing about a different family emoji. A measured VS16 sequence says nothing about every sequence containing VS16. This refusal to generalize is what makes the cache an observation rather than another predictive model.

A bound for safety, a measurement for layout

For every eligible measurement candidate, compute B = 2 × codepointCount(candidate). Require B < terminalColumns before sending any probe, leaving one cell beyond the bound so no prefix can fill the final column, arm pending wrap, wrap, or scroll. This gate applies on every terminal; a successful clustering sample or a cached final width does not bypass it. A candidate that cannot pass the gate becomes a placeholder without being printed or probed.

Accept a same-row observation only when 1 <= measuredWidth <= B. Widths such as eight are ordinary successful observations, not errors merely because they exceed two. Zero advance and values above the bound reject the batch. The bound is a supported-terminal assumption about ordinary text, not a Unicode width prediction or a property established by the probe.

Keep both Width = measuredWidth and RequiredCells = B + 1 on a resolved measured atom. Layout uses RequiredCells to decide whether to begin a new row, then advances by Width after painting. The guard and unused allowance are not printed padding; following text starts immediately after the measured final advance. The bound must protect intermediate prefixes even when the final measured width is only one cell. Generated tab text uses the codepoint count of ▸, so its bound is two and its required space is three.

Fixed printable ASCII and placeholders have Width and RequiredCells equal to one. Two-character caret notation has both equal to two; its known ASCII rendering needs no extra guard. A source hard break has both equal to zero. 

func ResolveGeneralInto(dst []DisplayAtom, missDst []string, command SourceText,
    cache *WidthCache, eligibility *CandidateEligibilityCache, columns Cells) ([]DisplayAtom, []string) {
    atoms := segmentAtomsInto(dst, command)
    // Proposed interface: resolution gates cached and unknown candidates by geometry.

Cache lifetime

The width cache lives in memory and normally spans prompts. It is tied to a width epoch: the period during which mshell owns and reasserts its terminal modes and assumes the terminal's width behavior is stable. Start a new epoch after terminal reattachment, resume when state cannot be trusted, or any explicit recalibration command. Resize alone does not change cluster width and does not clear the cache. It does require rechecking RequiredCells against the new column count, regenerating placeholders where needed, and recomputing all forced breaks. A geometry-skipped candidate stays eligible and may be measured after the terminal grows; geometry is not a permanent eligibility rejection.

Do not write the cache to disk in the first implementation. Correct invalidation across terminal upgrades, tmux attachments, font changes, and configuration is harder than remeasuring the small set of clusters a user actually types.

04

Measure a batch in one transaction

Resolve every distinct cache miss in the newest editor state before layout. A paste containing repeated clusters measures each distinct byte string once. All probes are emitted in one buffered write and all replies are then collected by the normal terminal-input lexer.

Resolution is resource-bounded. Measure at most a fixed number of distinct misses in one editor generation and cap both cache entries and candidate byte length. Overflow candidates use the known-width placeholder; they are not allowed to create an unbounded query burst or cache from an adversarial paste. A first implementation can use conservative constants such as 256 probes per generation and 4096 cache entries.

There is one CPR response per distinct unknown cluster, but the requests are not serialized. On SSH or ConPTY the batch can travel as roughly one additional transport round trip, independent of the number of misses in that batch. Ordinary cached or printable-ASCII edits pay no round trip.

Probe from a known cell

The renderer provides one owned scratch row outside the visible edit contents. Each probe clears pending wrap and moves to column one with CR, clears the scratch row, writes exactly one eligible candidate cluster, and requests CPR. There is no printed ASCII prefix. 

for cluster in misses:
    bound = 2 * codepointCount(cluster)
    require terminalColumns >= 4 && bound < terminalColumns
    write(CR + EL + cluster + CPR)
    write(CR + EL)

// One report per complete cluster; never probe its components or prefixes.
// Column numbers are one-based; bound is from this reply's candidate.
measuredWidth = replyColumn - 1
require replyRow == scratchRow
require 1 <= measuredWidth && measuredWidth <= bound

Raw newlines, tabs, C0/C1 controls, and ESC never enter this protocol. The generated tab glyph ▸ goes through the same eligibility check and width resolution as other candidates. CPR observes cursor advance only; neither the eligibility check nor the probe can detect arbitrary visual changes or prove behavior with every possible neighbor.

Four columns is the absolute minimum supported terminal width for both interactive painting and width probing. Below four columns, do not paint interactive contents or issue width probes; continue accepting editing keys or report that the terminal is too narrow.

The four-column minimum is necessary but not sufficient: each candidate must also pass the bound-plus-guard gate. At four columns a one-codepoint candidate has bound two and can be probed; a two-codepoint candidate has bound four and must use a placeholder. Never print an oversized candidate and rely on a changed reply row to detect wrapping afterward. Scrolling at the bottom of the screen can leave the reply on the same row and make a large advance look small. Bounding every prefix before output removes that ambiguity under the supported-terminal contract.

parseCursorReport validates CPR syntax and positive coordinates up to the supported limit of 9999. widthFromCursorReport must be extended to receive the candidate bound, require the expected scratch row, and accept any positive advance through that bound. It performs no I/O and makes no cache changes; the batch collector must establish reply ownership and decide whether measurements can be committed.

Scratch-row ownership

Do not use terminal save/restore-cursor state. Move relative to the renderer's known region, create or reuse a row immediately below the previous editing region, and account for a scroll if creating that row reaches the bottom of the screen. Clear the scratch row before leaving it. After replies are validated, repaint the editing region from its tracked origin.

The initial prompt can perform capability validation before showing editable text. Later cache misses temporarily leave the previous correct frame visible; mshell does not optimistically paint a layout with guessed widths.

Replies share the keyboard stream

While a batch is outstanding, the lexer routes CPR-shaped tokens to the resolver and queues ordinary input tokens. Count received reports separately from accepted widths, including reports that invalidate the batch and reports received after it has failed. Continue blocking reads until every expected report has arrived; there are no query deadlines, retry timers, or timeout-based recovery. After rejection, drain the remaining reports before starting another width batch or prompt-anchor query. A read/write error or EOF aborts the exchange and exits interactive mode through terminal cleanup. A generation number associates a requested layout with the editor state that requested it. If more input arrives before resolution completes and the complete batch validates, commit its measurements, discard the stale layout, apply queued input, and resolve the newest state. 

generation 41: measure ["❤️"]
keypress arrives: queue it; generation 41 is no longer the next frame to paint
generation 41 reply: cache "❤️" = 2; do not render generation 41
apply queued edits: generation 42; resolve remaining misses, layout once, render once

05

Two pure layout paths

Printable ASCII layout is direct byte and cell arithmetic. General layout begins only after every display atom has a known final width and a required-space bound, then uses integer arithmetic over indivisible atoms. Both functions are deterministic, allocation-conscious, and incapable of querying the terminal.

    dst       []LayoutRow,
    command   SourceText,
    cursor    ByteOffset,
    startCol  Cells,
    columns   Cells,
) LayoutResult

    dst       []LayoutRow,
    atoms     []DisplayAtom,
    cursor    ByteOffset,

    columns   Cells,

  • The printable-ASCII path may wrap at any byte boundary because each source byte is exactly one cell.
  • Every general-path text atom is a complete grapheme cluster, printable ASCII byte, generated control representation, or placeholder with a resolved width.
  • No general-path atom is split across rows, including an eight-cell cluster on a non-clustering terminal. Candidates whose RequiredCells exceed an empty row are placeholders before layout.
  • The first row begins at the measured prompt column; subsequent rows begin at column one. A forced break may leave the initial command row empty when the prompt leaves insufficient space.
  • Hard newlines are source atoms with explicit row semantics and zero printable width.
  • Conservative hard wraps are renderer-generated row endings. They insert no bytes into the source command and create no additional editing positions.
  • The cursor may land at any byte boundary on the printable-ASCII path and only at source grapheme boundaries on the general path; either maps to exactly one row and cell gap.
  • Every row width is at most the available terminal width.
  • For printable-ASCII input, both paths produce identical rows and cursor placement.

Hard-wrap before any atom that cannot safely fit

For an atom requiring at least two cells of space, if its RequiredCells exceed the remaining columns, layout ends the current row with a forced hard break and places the complete atom on the next row. The painter emits CRLF for that break before emitting any byte of the atom. This applies in all terminal modes, including every atom of width two or more that does not fit. For measured text the decision uses B + 1, not merely the final measured width: even a final width of one can have a wider intermediate prefix. Fixed two-cell caret notation hard-wraps whenever fewer than two columns remain. 

// Source hard-break atoms are handled separately with CRLF.
// Resolution already ensures atom.RequiredCells <= columns.
remaining = columns - col
if atom.RequiredCells > remaining:
    if atom.RequiredCells == 1 && col == columns:
        endRow(SoftExact)   // Printing this known one-cell atom triggers autowrap.
    else:
        endRow(ForcedHardWrap)  // Painter emits CRLF, clearing any pending wrap.
    col = 0
place(atom)
col += atom.Width         // No padding for unused bound or guard space.

For a seven-codepoint cluster measured at eight cells, RequiredCells is fifteen. With three columns remaining, hard-wrap first; with fifteen remaining, print there and advance only eight cells. With only fourteen columns in the entire terminal, display a one-cell placeholder instead. No component widths, prefix measurements, or clustering-mode boolean are needed to predict splitting because the cluster is never allowed to split.

Keep simple ASCII wrapping separate

Known one-cell ASCII and placeholders can still use ordinary terminal autowrap when a preceding row is exactly full; the direct printable-ASCII layout remains valid. Represent natural exact wraps, forced hard wraps, source hard breaks, and final row endings distinctly so the painter knows when to emit CRLF. Known ASCII output can arm pending wrap at the final column; record it explicitly and cancel it with CR before relative repositioning or a forced CRLF. A forced CRLF after an exact fill advances one row, not two; do not additionally trigger autowrap for that same row transition. Measured atoms never arm pending wrap because their entire possible advance leaves the guard cell unused.

Renderer-generated CRLF changes screen presentation only; submission uses the original UTF-8 source. Selection/copy may include these visual line breaks, and terminals may not rejoin them during resize reflow. Accept that tradeoff in favor of predictable placement, then re-anchor and repaint from the source after resize rather than trusting reflow to reproduce the layout.

Full-region repaint first

Start with a whole-region repaint assembled into one output buffer. Home to the known origin with relative movement, paint safe source slices and placeholders with the layout's explicit row transitions, erase renderer-owned leftovers, and park the cursor from the layout result. A later desired-versus-actual diff renderer can consume the same layout without changing width resolution.

Styling is orthogonal

Syntax highlighting produces style spans over source byte offsets. The painter intersects those spans with layout atoms and emits SGR only while painting. SGR bytes have no width and never appear in SourceText, segmentation, the width cache, or layout arithmetic.

The more detailed paint-domain vocabulary and region-rendering figures remain in render-pipeline.html. This document supersedes that document wherever it proposes predictive cluster/codepoint width parameters or preserving natural soft wraps for every atom.

Atomic batch rejection

Stage observations outside the width cache until every expected reply has arrived and the complete batch has validated. A malformed reply, unexpected row, zero or above-bound observed width, or terminal I/O failure rejects all measurements from that batch, including individually valid observations. Previously cached widths and all candidate eligibility decisions remain intact. On a validation failure, drain all remaining expected reports, recover the owned terminal region, and use placeholders for widths that remain unknown. I/O failure or EOF takes the cleanup-and-exit path rather than waiting for reports that can no longer be read. An editor generation change alone is not a measurement failure: commit a valid batch but discard its stale layout.

Retry only after command submission

A failed width batch sets a per-command widthProbesBlocked flag. Subsequent edits continue using cached widths and placeholders without issuing new width probes. Clear the flag when the command is submitted and the editor begins a new prompt, allowing unknown widths needed by the next command to be measured again. Enter that merely inserts a newline into an unfinished command does not clear the flag. Neither cache is cleared by this reset, and failed measurements remain unknown rather than becoming permanently rejected eligibility entries.

There is no retry timer or cooldown. There are no read deadlines or query timeouts: the terminal is required to eventually answer every request. Received-report counting drains a rejected batch before any subsequent query, including prompt anchoring, can start. Clearing the flag permits another measurement attempt; it does not bypass that drain. Eligibility rejection, resource limits, and insufficient terminal width skip candidates or probes without constituting a failed batch.

The placeholder changes display text but not source text. Submission still uses the original UTF-8 bytes. A placeholder atom retains the source start/end offsets of the cluster it represents, so cursor movement and editing remain structurally correct.

Raw controls are never painted

Raw terminal controls cannot be allowed into the paint stream. They remain in SourceText because editing and submission operate on the exact command. Resolution turns C0 controls and DEL into AtomControl values using two-cell ASCII caret notation: NUL is ^@, Ctrl-Z is ^Z, ESC is ^[, and DEL is ^?. Tab is the exception: it paints as ▸, whose exact width is measured and cached for the terminal epoch using the same bound and guard rules. C1 controls use a fixed printable ASCII fallback in the first implementation; their source bytes are still preserved. Literal newlines are explicit hard-break atoms. The painter must never copy an AtomControl's source slice to the terminal device.

What correctness means here

  • mshell never calls a Unicode table's width estimate an observed terminal width.
  • Every painted non-ASCII cluster has either an exact cache entry from this terminal epoch or a known-width ASCII placeholder.
  • Every layout is computed from the same widths the painter will emit.
  • A failed or stale measurement can delay or degrade one frame, but cannot corrupt future row bookkeeping.
  • Terminal-specific behavior is contained in one resolver instead of leaking through layout and rendering.

Implementation order

  2. Add RequiredCells and geometry gating to resolution; widen observation/cache validation to accept positive whole-cluster widths through the candidate bound.
  3. Adapt general layout and tests to RequiredCells, widths above two, and distinct forced hard-wrap row endings while retaining row-storage reuse.
  4. Complete grapheme-boundary handling for insertion, replacement, and word operations, and the conversion from the current rune cursor to source byte offsets.
  5. Build bounded whole-cluster probe emission, scratch-row ownership, and reply draining against a fake terminal and PTY tests; do not introduce timeouts or prefix probes.
  6. Connect session caches, queued edits/generation handling, per-command probe blocking, and geometry-dependent placeholders to completed layouts.
  7. Swap the interactive renderer to region-relative repainting with explicit CRLF for forced breaks, including history suggestions and completion geometry.
  8. Add terminal-mode lifecycle and platform backends without changing the width/layout interfaces.
  9. Run the real-terminal matrix and only then remove the old renderer.

Current implementation checkpoint

As of commit 2132e97, pure ASCII and atom layout, segmentation, eligibility/cache helpers, and placeholder resolution exist. Session-owned display storage and caches, command preparation, and guarded ASCII layout are connected to the interactive loop alongside the old renderer. Prompt queries send one request and queue keyboard input; the unused read deadline has been removed. Batch collection counts reports independently of accepted widths, drains rejected batches, and sets a probe block that resets on command submission. Left/Right Arrow, Ctrl-B/Ctrl-F, Backspace, and Delete use grapheme boundaries, including resegmentation after deletion.

This revision is a target design, not a claim that conservative wrapping is already implemented. Observation/cache helpers and general layout still impose the old one-or-two-cell limits; RequiredCells, bound-plus-guard gates, and forced hard-wrap row endings are not implemented yet. No code starts a width batch or emits the proposed probes, and the live renderer still uses the old painting and cursor-position arithmetic. General layout integration, remaining editing paths, byte-offset migration, scratch ownership, resize, and terminal-mode lifecycle remain work. Existing pure helpers accept terminal widths two and three as mathematical test cases, but interactive support still starts at four columns.

08

Test the boundaries, not a model

Pure unit and property tests

  • Printable-ASCII classification accepts exactly bytes 0x20 through 0x7e; tab, newline, other controls, DEL, and every non-ASCII byte select the general path.
  • Direct printable-ASCII layout creates no display atoms and produces the same rows and cursor placement as the general atom path for printable-ASCII inputs.
  • Every C0 control and DEL retains its byte range, resolves to the correct safe representation, and can never place the raw control byte in ScreenBytes.
  • Tab paints as ▸; cache hits, exact measurement, rejected-batch fallback, and one- versus two-cell observations preserve source offsets and use RequiredCells of three before fallback.
  • At a mixed ASCII/non-ASCII boundary, classify without constructing partial atoms and segment the complete buffer so combining marks can join the final ASCII base.
  • Segment every stress string and verify atoms tile source bytes exactly.
  • Inject widths from one through each candidate's bound, including widths such as eight; never call a terminal from layout tests.
  • For every grapheme-boundary cursor position and supported terminal width at least four, rows stay within bounds and the cursor lands on a valid cell gap. Pure layout tests may additionally exercise widths two and three.
  • Source hard breaks, renderer-forced hard wraps, exact one-cell soft fills, trailing newlines, and first-row prompt offsets retain distinct row semantics.
  • A multi-cell atom with insufficient remaining space always gets CRLF before any of its bytes, including generated two-cell caret text.
  • Measured width one still obeys its larger bound plus guard; a prefix that temporarily advances two cells must never reach the margin merely because the final advance shrinks to one.
  • A seven-codepoint cluster measured at eight cells needs fifteen available columns, consumes only eight, hard-wraps with three remaining, and becomes a placeholder on a fourteen-column terminal.
  • Bound equal to terminal width is skipped; bound one less than terminal width is allowed. Equality of RequiredCells and remaining space is allowed without emitting padding.
  • Cached clusters become placeholders when resize makes their RequiredCells too large, then reuse their cached width when space is available again.
  • Movement, word operations, insertion, replacement, and deletion preserve grapheme boundaries regardless of measured width or fallback; deleting an eight-cell cluster removes it in one operation.
  • Cache deduplication measures each exact cluster once per epoch.
  • Eligibility accepts an accent with its base and rejects a standalone accent; rejected atoms never enter the probe list and retain their source ranges.
  • Eligibility caches both true and false decisions, survives width-cache epoch changes, and rejects unseen candidates without segmentation when full.
  • Probe, cache-entry, and candidate-length limits always produce placeholders rather than unbounded work.
  • Editing that changes segmentation re-derives boundaries and does not reuse a cache entry for a different byte string.
  • Resolution and layout reuse caller-provided backing arrays without retaining stale atoms or rows.

Performance benchmarks

  • Benchmark short all-ASCII commands representative of interactive typing, not only large throughput inputs.
  • Benchmark mixed input whose first non-ASCII byte occurs near the beginning and near the end.
  • Benchmark large ASCII and Unicode pastes with allocation counts and bytes per operation reported.
  • Use the scalar printable-ASCII classifier as the baseline; compare word-at-a-time or SIMD validation against it before increasing complexity.
  • Keep the direct ASCII path allocation-free apart from caller-owned row capacity; optimize the general path independently when profiles justify it.

Protocol tests with a fake terminal

  • Several probes are written before any reply is required.
  • Replies populate the correct cache keys even when keypress tokens are interleaved.
  • Malformed reply, wrong row, zero/above-bound advance, and terminal I/O failure discard the entire batch, including otherwise valid observations; preexisting width and eligibility entries remain intact.
  • A failed batch blocks new width probes during subsequent edits of the same command; cached widths and placeholders remain usable.
  • Submitting a command and beginning the next prompt clears the probe block; inserting a multiline newline does not. Retry requires draining the prior batch and uses no timer.
  • Delayed replies from a rejected batch are counted and drained before a new batch or prompt-anchor query; keyboard tokens remain queued in order.
  • Arbitrarily slow replies do not cause retries, fallbacks, or duplicate requests; fake input delivers eventual reports without relying on wall-clock timeout tests.
  • Probes contain no ASCII prefix and no partial-cluster measurements. Reply column nine is accepted as width eight for a candidate with a sufficient bound.
  • Below four columns, neither interactive painting nor width probing is allowed. At four columns, a two-codepoint candidate is never sent, while a one-codepoint candidate reporting column four violates its bound and rejects the batch.
  • Even with the scratch row at the bottom, every permitted probe leaves a guard cell and causes no wrapping or scrolling. Oversized candidates emit no source bytes.
  • Forced CRLF after pending wrap advances exactly one row, and measured text is never left to wrap internally.
  • A stale generation retains valid measurements but never paints its stale layout.
  • The scratch row is cleared and terminal mode is restored on every exit path.

Real-terminal matrix

Run the existing tests/terminal_tests/width_report.py and the new DSR/CPR latency harness in each target environment. Then exercise the actual editor through a PTY with ASCII, combining text, CJK, VS15/VS16, flags, skin tones, keycaps, ZWJ sequences, paste, resize, tmux, SSH, and ConPTY. Include terminals that cluster and terminals that render components separately, clusters wider than two cells, narrow-window fallback, delayed CPR, bottom-row probing, and hard-wrap selection/reflow behavior. A terminal that ignores CPR is outside the supported contract and is not expected to recover automatically.

Rejected designs

ApproachReason
Infer a terminal-wide width profile from representative probes.Fewer queries, but correctness depends on unproved equivalence classes.
Use uniseg's cluster width after segmentation.It describes uniseg's tables, not the current terminal.
Measure every occurrence.Correct but needlessly repeats I/O; exact session caching is simpler.
Serialize one probe and wait before sending the next.Turns a paste into many network round trips.
Optimistically render predicted widths, then repair.Allows a wrong wrap to corrupt the frame and complicates recovery.
Persist measurements by terminal identity.Invalidation is harder than remeasurement and silently risks stale geometry.
Split an oversized grapheme into codepoints.Violates the complete-cluster rendering invariant.
Infer internal wrapping from prefix-width differences.Later codepoints can modify earlier widths; conservative whole-cluster placement avoids needing a component model.
Pre-wrap using only the final measured width.An intermediate prefix can be wider and trigger wrapping before the final width is established; use the bound plus guard instead.
