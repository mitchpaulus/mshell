Design proposal · August 2026

Progress that behaves like a shell.

A batteries-included, scoped API for spinners, measurable progress, task trees, and durable log output—designed around mshell’s stack, quotations, typed shapes, and stream semantics.

Recommendation
One coordinated progress scope, not independent printing widgets. A progress. quotation owns rendering and cleanup; lightweight ProgressTask handles describe state. Live terminals redraw in place. Pipes, files, dumb terminals, and CI receive an append-only transcript.

The direction

The hard part is not drawing a bar. It is making progress coexist with logs, redirected streams, child processes, narrow terminals, failures, and Ctrl+C. The API should make the correct lifetime impossible to forget.

Scoped by default

progress. starts the renderer, executes one quotation, then restores cursor and terminal state on success, language failure, or interruption.

stderr is presentation

The live display defaults to effective stderr. Stdout remains clean for data pipelines—the normal expectation for a shell.

State, not escape codes

User code updates task objects. One renderer owns cursor movement, width measurement, throttling, and output interleaving.

Graceful degradation

Non-interactive output is useful text, never a stream of carriage returns and never silently absent unless explicitly requested.

Concatenative vocabulary

Objects come first, modifiers follow: @task 1 progressAdvance, @task "Linking" progressMessage.

Rendering, not orchestration

mshell remains responsible for sequencing, branching, retries, rollback, and future parallel execution. This API reports what that code is doing.

The experience

The default display is quiet enough for everyday shell scripts and rich enough for a release or deployment. It adapts columns to available width rather than wrapping a task into a broken two-line bar.

Two opaque values

Progress is a rendering session. ProgressTask is a reference to one task owned by that session. Both are named runtime types, following the precedent of Grid, GridView, and GridRow.

Progress

Owns the task tree, effective output target, render mode, refresh clock, width cache, cursor visibility, line-buffering writers, and cleanup. Only one scope may render to a given terminal at once.

ProgressTask

A small handle into session state. Copies refer to the same task. It becomes invalid when its session closes; use afterward is a clear runtime error.

Task lifecycle

pending→running→succeeded orfailedorwarnedorskippedorcancelled

A task starts as pending. The first update starts it automatically, while progressStart is available when “started but still at zero” matters. Terminal states are final and idempotent only when repeated with the same state; contradictory transitions fail loudly.

A task without a total is indeterminate and renders as a spinner. Setting a total converts it to determinate progress. Setting position to or beyond total does not mark it successful; completion is an explicit semantic event.

Parent and child tasks

Tasks may have children. A parent with no explicit position derives a summary from its children and remains running while any child runs. It succeeds only when explicitly completed; failures are visually propagated upward but never silently change shell control flow.

Proposed API

The small core is built in. Convenience combinators can live in lib/std.msh when they are expressible in terms of the core. Signatures below use the modern type spelling for clarity.

WordStack effects and meaning

Scope options

Options use the repository’s optional-shape convention. Unknown keys are errors when statically known and runtime errors otherwise.

type ProgressOptions = {
    mode?: str,              # "auto" | "live" | "plain" | "json" | "silent"
    target?: str,            # "stderr" (default) | "stdout"
    transient?: bool,        # clear live display when scope closes; default false
    keepCompleted?: int,     # visible completed rows; -1 = all, default 20
    refreshHz?: float,       # default 12; renderer clamps to a safe range
    columns?: [str],         # ordered built-in column names
    color?: str,             # "auto" | "always" | "never"
    unicode?: str,           # "auto" | "always" | "never"
    plainUpdates?: bool,     # include percentage milestones in plain mode
    minDuration?: float      # suppress fast success only if no update occurred; default 0.10s
}

Built-in columns are state, tree, message, bar, position, percent, elapsed, eta, rate, and output. Presets in the standard library—progressDefault, progressCompact, and progressBytes—are ordinary option dictionaries.

It should read like mshell

One spinner, automatic cleanup

progress.
    p!
    @p "Resolve dependencies" progressTask task!
    @task progressStep.
        ['go' 'mod' 'download']!
    end
end

Measurable work

{ "columns": ["state" "message" "bar" "position" "eta"] } progressWith.
    p!
    @p files "Hash files" progressEach. file!, task!
        @task @file str progressOutput
        @file sha256sum drop
    end
end

The quote receives the item below ProgressTask, so the comma store preserves the readable names: file!, task!. If an iteration fails, progressEach marks the task failed and propagates that failure without advancing it.

Nested task tree and a handled failure

progress.
    p!
    @p "Build release" progressTask build!
    @build "Compile" progressChild compile!
    @build "Test" progressChild test!

    @compile progressStep. ['go' 'build' './...']! end

    @test progressStart
    ['./test.sh']? status!
    @status 0 = if
        @test progressDone
    else
        @test $"test suite exited {@status}" progressFail
        @build "release is not publishable" progressFail
        @status exit
    end

    @build progressDone
end

Logging while a display is live

@p "info" "cache hit for 142 of 180 modules" progressLog

# Ordinary writes are also safe. They keep their original stream.
"machine-readable-result" wl
"compiler warning" wle
Why the session is passed into the quote: it makes ownership explicit, nests naturally with prefix quotations, and allows the type checker to reject task creation outside a live scope. The quote has a clean stack containing exactly one Progress, matching the convention used by definition-based completions.

Rendering contract

The renderer is part of the behavioral API, not cosmetic implementation detail.

Auto mode

Use live rendering only when the chosen effective target is a terminal/console, TERM is not dumb, and the environment can support cursor movement. Otherwise use plain. NO_COLOR disables color but not Unicode or progress itself. Explicit options override detection.

Fallback

ASCII substitutions are stable: + success, x failure, ! warning, - skipped, |/-\ spinner, #- bar. Color is never the sole carrier of state.

Width

Measure terminal cell width, not UTF-8 bytes. Drop columns in this order: output, rate, ETA, position, elapsed, bar, percent. The state glyph and an ellipsized message always survive. Tree indentation collapses on very narrow terminals.

Refresh

State mutations are cheap and request a redraw. A single render loop coalesces updates and redraws at most refreshHz. Terminal resize triggers immediate layout. No user quotation executes on the render goroutine.

Estimate

Rate and ETA use an exponentially weighted moving average with a short warm-up. A reset or large backward progressSet resets the estimator. Paused time is excluded if pause/resume is added later.

Safety

Messages are plain text in v1. Newlines become separate indented detail lines; non-SGR terminal control sequences are escaped. Styling is semantic and renderer-owned, avoiding a markup language and terminal-injection surprises.

Streams, logs, and child processes

Inside the scope, mshell wraps the effective stdout and stderr in line-aware writers. Before a complete line is emitted, the live region is cleared; the original bytes go to their original stream; the region is redrawn below. Partial lines are buffered only until flush/scope close, with a bounded buffer.

For a child whose output can be connected through io.Writer, the same coordination applies. When a foreground child needs a real terminal file descriptor—an editor, pager, prompt, or full-screen TUI—the progress renderer suspends completely, restores cursor state, hands off the terminal through the existing foreground-control machinery, and redraws after reclamation.

Redirected quotations and commands keep their documented semantics. The progress target is resolved from the scope’s effective stream, so (...progress...) `build.log` 2> x naturally selects the plain renderer and writes the transcript to that file.

One unresolved implementation detail: I did not find a documented public “flush partial line” operation. The scope therefore needs to flush partial buffered output on close, before child terminal handoff, and before a prompt. If mshell later exposes unbuffered stream objects, it should also expose an explicit flush hook.

Errors and interruption

progress and progressWith act like defer boundaries. They must restore the cursor and remove the live area even when the quotation returns a failing EvalResult. Any running tasks become failed on language/runtime error and cancelled on Ctrl+C; the original error or signal behavior is then propagated unchanged. Cleanup errors are reported without replacing the original failure.

In plain mode, minDuration may suppress only a fast successful task that had no intervening update. The renderer buffers its initial START; the first progressStart, progressSet, progressAdvance, progressTotal, progressMessage, or progressOutput flushes that start and guarantees a transcript, even if the task completes before minDuration. Explicit logs are always emitted.

Nested progress scopes targeting the same terminal do not create a second renderer. They attach a child group to the active scope. A nested scope with a different redirected target is independent.

Implementation shape

  1. Runtime objects. Add MShellProgress and MShellProgressTask, session identity checks, a mutex-protected state tree, and named static types.
  2. Scoped evaluation. Implement progress and progressWith as quotation-evaluating built-ins with a clean one-item stack, guaranteed finalization, and original EvalResult propagation.
  3. Renderer. One goroutine owns ticks and terminal writes. Mutators only update state and signal a buffered dirty channel. Render frames into lines, diff against the prior frame, and use cursor movement rather than scrolling.
  4. Stream coordination. Add progress-aware writers to ExecuteContext. Reuse effective-stream terminal detection and the foreground terminal controller instead of checking global os.Stdout/os.Stderr.
  5. Type checking. Register the two named object types and the fixed builtin signatures using the existing type infrastructure. Enforce concrete optional option shapes. Both scope words require (Progress -- ); progressStep requires (() -- ). No row polymorphism, binding propagation, or new resolution rule is required.
  6. Portable backends. ANSI/VT on POSIX and modern Windows consoles, ASCII/plain fallback everywhere. No alternate screen buffer.

State snapshot

progressSnapshot returns a shape suitable for assertions, JSON serialization, and future external renderers:

{
  "mode": "plain",
  "tasks": [{
    "id": 2, "parentId": 1, "state": "running",
    "message": "Bundle assets", "position": 128, "total": 180,
    "elapsed": 2.7, "rate": 35.8, "output": "icons.svg"
  }]
}

IDs are session-local integers and ordering is insertion order. Time-dependent values can be normalized or ignored by tests; the JSON-lines renderer emits state-change events with the same vocabulary.

Verification

  • Golden tests for live frame layout at narrow, normal, and resized widths; ASCII and Unicode modes.
  • PTY integration tests for log interleaving, partial writes, Ctrl+C, cursor restoration, foreground child handoff, and nested scopes.
  • Redirect/capture tests proving stdout data stays unchanged and stderr transcripts contain no ANSI in auto/plain mode.
  • Race tests with concurrent state updates once parallel execution can expose task handles to isolated workers.
  • Fake clock tests for refresh throttling, elapsed time, rate/ETA, and minDuration.

Scope and rollout

V1

Scoped session, root and child tasks, spinner/bar modes, lifecycle verbs, tracked iteration, logs and volatile output, live/plain/silent rendering, adaptive default columns, stream coordination, snapshots, and robust cleanup.

V1.1 candidates

JSON-lines renderer; a result-preserving progressMap; byte-copy helpers once mshell has a streaming API; pause/resume; task removal; user-selectable semantic theme; integration with the proposed parallel executable.

Explicit non-goals

  • No arbitrary Rich-style widgets, tables, Markdown, or user quotation columns in the render loop.
  • No retry, rollback, dependency graph, concurrency scheduler, or cancellation engine.
  • No alternate-screen TUI and no prompt implementation.
  • No parsing of arbitrary child output to infer progress.
  • No silent non-TTY default; choose mode: "silent" explicitly.

Settled decisions

Naming

Every public operation uses the complete progress* family: progressTask, progressAdvance, progressDone, and so on. There are no short aliases such as advance or done.

Failure

Progress does not add a new way to fail the program. Ordinary mshell mechanisms—!, ?, exit, and evaluator failures—retain control-flow authority. progressFail only records and renders a task’s failed state; it does not fail execution.

Fast tasks

In plain mode, minDuration applies only when a successful task had no actual update after creation. Any explicit start, position, advance, total, message, or output update emits the buffered START and guarantees the task’s transcript.

Quote stack

The scope quote is isolated and balanced: it starts with exactly one Progress and must finish empty. It cannot consume the caller’s existing stack or return values on the data stack. Both scope words use ordinary fixed quotation signatures, so the type checker needs no new mechanism.

Returning data through existing variables

The quotation is constructed in the outer variable scope, so it can read and update variables already known there. Declare a result with its intended type before entering progress, then assign it inside while keeping the quotation stack balanced:

"" checksum!

progress.
    p!
    @p "Package" progressTask task!
    @task progressStep. ['make' 'package']! end
    `dist/app.zip` sha256sum checksum!
end

@checksum wl

This uses current runtime and checker behavior: quotations capture outer variables, and the outer binding already establishes the type of @checksum. A progress quote should not introduce a brand-new variable that is expected to be readable afterward, nor change an existing variable to a different type. Those cases would require binding propagation changes that are outside this design.

Consequences

  • progress remains a control and presentation boundary rather than a data-stack combinator.
  • A stray drop cannot consume caller data because the quote has its own stack.
  • Leaving any value behind is a normal quotation stack-effect error.
  • On evaluator failure or Ctrl+C, rendering is finalized and the original failure propagates; progress does not roll back variable mutations already performed by the quote.
  • progressWith behaves identically; its options dictionary is not visible inside the quote.
