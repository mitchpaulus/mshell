Exploration update · 2026-09-14

This records the direction reached in discussion, not an implemented feature or a completed soundness proof. The original type-checker design and implementation plan remain unchanged; their accepted aliasing hole conflicts with the stricter goal recorded here.

mshell examples involving tryAs and the proposed structural type syntax describe intended behavior. Checker-state displays are explanatory notation, not new language syntax.

1. Agreed direction

A program that passes checking must not later fail with an actual type error because a mutation invalidated a fact the checker relied on.

Rejecting some programs that would run successfully is acceptable. Accepting a program that later adds an integer to a string because of stale container information is not.

The preferred experiment is an evaluator-style checker: follow definition bodies at calls, using abstract values and shared storage identities. Retain declared signatures to check intent and catch bad inputs at useful boundaries.

  • Keep shared mutable containers at runtime.
  • Track changes to the facts about those containers.
  • Invalidate facts when a potentially conflicting write occurs.
  • Reject operations whose required facts can no longer be established.
  • Start without public effect annotations or a system of reusable mutation summaries.

This is symbolic execution over an approximation of program state, also called abstract interpretation. It executes neither external commands nor file operations during checking.

2. Both checks on definitions

StagePurpose
Definition checkAnalyze the body against declared inputs and outputs to check its contract.
Call boundary checkReject immediately when actual arguments do not satisfy the input requirements.
Call-specific body analysisFollow the body using the caller's actual reference relationships; propagate mutations and output references back to the caller.

A signature remains useful documentation and an enforced contract. It is not a complete account of what happens to shared storage during a call.

For this exploration, an ordinary container parameter describes requirements at entry. A body may change those contents if the checker accounts for the change and no persistent obligation is violated. Declared outputs must hold at successful return.

Definition parameters might alias

The initial check cannot assume that two parameters represent different objects. It must analyze possible aliasing conservatively, or retain an explicit obligation for call-specific checking. Passing the signature check alone cannot discharge a deferred alias-dependent obligation.

def writeThenRead ({age: int} {age: int} -- int)
    left!, right!
    @left "age" "old" set drop
    @right :age? 1 +
end

{"age": 42} dup writeThenRead

At this call, both arguments reference the same dictionary. The write therefore makes the subsequent arithmetic invalid inside the body. A later implementation could accept calls with definitely distinct dictionaries by checking their actual alias relationships.

Optional signatures were discussed, but are not needed to test this approach. Keep the existing signature surface for the initial prototype; signature omission is a separate decision.

3. Validation and a shared list

[1 2 3] as [int | str] mixed!
@mixed tryAs [int] ? integers!
@mixed "hello" append drop
@integers (1 +) map

The declaration permits strings, but validation establishes that the current contents are integers. Validation returns the same list, so both names reference storage L.

Point in programShared stateResult
Before validationmixed → LList described as [int | str].
Successful validation and unwrapmixed → L; integers → LCurrent contents known to be integers.

A saved successful check is not a permanent certificate

@mixed tryAs [int] result!
@mixed "hello" append drop
@result ? (1 +) map

Even if result is just, its payload still references L. Unwrapping it later must not restore the old integer-only fact. Evidence of a successful check must remain associated with the storage it checked and be invalidated by relevant writes.

If a scalar integer was extracted before a mutation, that scalar stays an integer. An extracted child list or dictionary remains a tracked reference.

4. Mutation inside a definition

def overwriteAge ({name: str, *: int | str} --)
    "age" "old" set drop
end

{"name": "Ada", "age": 42}
dup overwriteAge
:age? 1 +

The parameter permits the write, so checking only the body against that parameter type misses the caller's later problem. Call-specific analysis preserves the dictionary's identity through the call.

Before call:
    Stack: D D
    Storage: D → {name: str, age: int}

Follow overwriteAge:
    "age" "old" set → D.age becomes str
    drop            → consume one reference to D

After call:
    Stack: D
    Storage: D → {name: str, age: str}

:age? → str
1 +   → type error

The call can be allowed while the later arithmetic is rejected. No effect annotation is necessary to discover the write.

5. Shared storage, not copied types

The checker needs more than a stack of type descriptions.

Stack and variables: abstract values and references to storage
Storage:             current fields, element types, and child references
Evidence:            validation facts and their storage dependencies
Provenance:          where facts were established or changed
Effects:             possible I/O and failure paths, as a later extension

dup, variable retrieval, getters, indexing, Maybe payloads, and enum payloads must preserve reference relationships. Returning a new outer container does not imply that its children are new.

[1 2] child!
[@child] outer!
@outer :0: "bad" append drop
@child (1 +) map

The getter reaches the same child list as @child. Its mutation invalidates integer-only facts about the child and any deep validation of the outer list that depends on those facts.

Precise and uncertain writes

  • A known-key write to one definitely identified dictionary can replace that field's current type.
  • An append adds the new element's type to the list's possible contents.
  • A dynamic-key write conservatively affects every field the key could name, plus possible extra entries.
  • If a reference might point to A or B, account for a possible write to either; do not assume both were definitely overwritten.
  • A checker location representing multiple runtime allocations requires conservative updates, even though it has one internal ID.

Values that carry relevant references

ValueRelevant state
List / dictionaryMutable entries and potentially mutable children.
GridCells, columns, schema, and grid/column metadata dictionaries.
GridView / GridRowReferences to a backing Grid whose state may change.
Maybe / proposed enumA stable wrapper or tag can hold a reference to mutable storage.
QuotationCaptured variable cells and effects when executed.

Even scalar-only Grid cells would not eliminate schema effects or metadata aliases. The current implementation does not uniformly enforce scalar-only cells: generic column storage accepts arbitrary objects through some paths, while operations such as updateCol reject container results.

Quotations capture a variable map by reference. Rebinding a captured variable can change the object a quotation accesses later, so tracking only container identities at quotation creation is insufficient.

6. Branches, loops, and recursion

Following bodies directly is the preferred starting point for small scripts. The checker does not reproduce runtime iteration counts or perform actual I/O.

ConstructAnalysis
Ordinary callFollow the body with caller-specific references and a fresh local scope.
Unknown conditionAnalyze both reachable alternatives and combine possible storage states.
LoopInclude changes from previous iterations and reanalyze until a conservative state stabilizes.
Recursive callUse an evolving approximation at the recursion boundary rather than expand forever.
CallbackApply the quotation's effects when it executes, accounting for captures and repeated invocation.
 
[1] xs!
(
    @xs (1 +) map drop
    @xs "bad" append drop
    @stop if break end
) loop

Assuming stop is a bound boolean, a second iteration might perform arithmetic after the string append. Checking just the first iteration would be unsound.

A recursive signature can bound stack inputs and outputs, but it does not describe mutations to other live references. Recursion therefore needs storage approximations too, or must be rejected when those effects are unsupported.

Analysis limits must produce conservative loss of precision or an explicit rejection, never acceptance with incomplete facts. Cache summaries only if measurements justify it, and include the relevant alias and storage context in any reuse rule.

7. Persistent payload contracts

Recommended rule, still requiring detailed design: preserve an enum's declared mutable-payload contract through every alias.

If an enum promises a dictionary payload with age: int, wrapping D introduces an obligation that D's age remain an integer while that promise can be observed. A conflicting write through another reference must be rejected.

This differs from an ordinary local validation fact, which can be invalidated when storage changes. Constructor patterns rely on the declared payload type, so silently forgetting that contract would be unsafe.

Obligations must extend through nested mutable children. A conservative first version could keep an obligation once introduced rather than attempt to prove when the final dependent reference disappears.

The prototype can exclude mutable enum payloads initially. Supporting them safely is a required follow-on before claiming the complete nominal-plus-validation design is covered.

8. Errors with useful locations

Retain signatures to reject obvious input mismatches at the call boundary. For mutation-related errors, keep the origin of type changes alongside their current descriptions.

Cannot add int to str.
  At: :age? 1 +

The dictionary's "age" field became str at:
  dup overwriteAge

Inside overwriteAge:
  "age" "old" set

A call stack alone is insufficient: the mutation may have occurred in an earlier call that has already returned. Report the incompatible use, the write that invalidated its assumption, and the reference relationship connecting them.

Distinguish a demonstrated conflict from a conservative rejection such as “this callback may change the validated list; its element type is no longer known.”

9. I/O and possible failures

The same traversal can collect effects beyond mutation. This is a planned extension point, not a requirement to add public effect syntax now.

def loadNames (path -- [str])
    readFile lines
end
Stack:       path → [str]
I/O:         reads a file
May fail:    file read
Mutation:    no changes to caller-owned containers
def requireInt (str -- int)
    toInt ?
end

requireInt may fail when unwrapping a missing parse result. This is an intentional operational failure, not evidence that an integer operation received a string after successful checking.

  • Calls include effects from the called body.
  • Creating a quotation records its latent effects; executing it applies them.
  • Unknown branches contribute every possible effect.
  • If failure handlers are supported, remove only the failure cases actually handled and retain effects of the handler itself.
  • External command execution has opaque behavior beyond its declared interface; record execution and failure possibilities conservatively.

Go builtins need an explicit inventory of their effects and failure paths. Symbolic traversal propagates those descriptions; it does not automatically derive them from arbitrary Go code.

Initially, possible I/O and operational failures should be reportable information. Mandatory handling or optional “no I/O” and “no unhandled failures” contracts can be separate future decisions.

10. Guarantee and boundaries

The desired guarantee excludes actual type errors in accepted programs, including stale assumptions about shared containers. It does not promise successful file access, successful validation, valid indexes in every execution, or unlimited resources.

A terminating automatic checker for unrestricted programs cannot accept every semantically safe program while rejecting every unsafe one. We choose conservative rejection when proof is unavailable. This does not make the simple aliasing examples undecidable; it constrains what can be promised for all possible programs.

The guarantee requires every relevant mutation path to be modeled or rejected. Unknown code, untracked concurrent writes, and unchecked execution cannot be allowed to invalidate typed facts silently.

Partial execution and the REPL

Persist shared storage and variable relationships between successful REPL lines. A failed line can leave partial mutations behind, so its old state and predicted successful post-state may both be wrong. Conservatively invalidate affected facts, reconstruct them through supported inspection, or reset the checked session.

If an operational failure can be caught and execution resumes, its intermediate storage effects must similarly reach the handler. A whole-program type-safety claim also requires auditing existing inference rules, builtin signatures, and runtime representations beyond mutation.

11. A bounded prototype

Build a separate experimental checker before replacing the existing implementation. Keep the language surface small and make the abstract storage state inspectable.

  1. Represent scalar values, lists, dictionaries, shared references, and variable bindings.
  2. Implement known-key reads/writes, list writes, dup, stores, and retrieves.
  3. Retain signature boundary checks and walk nonrecursive definitions at calls.
  4. Add validation facts, invalidation, and reference-preserving Maybe results.
  5. Add conservative branch joins and a bounded, sound loop analysis.
  6. Expand to nested containers, quotations, recursion, Grids, and persistent payload obligations.
  7. Collect I/O and failure information after mutation safety works.

Unsupported cases must be rejected explicitly while the prototype is incomplete.
