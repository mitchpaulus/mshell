# Audit: archives, HTTP, output and miscellaneous

All line numbers are in `mshell/Evaluator.go` unless another file is named.
Old sigs are from `mshell/TypeBuiltins.go`; seed sigs are from `mshell/TypeCoreBuiltins.go`.

Shorthands used in the table:

- `Pack` = `[str | path | {path: str | path, archivePath?: str | path, mode?: int}]`
- `TarDest` = `str | path | {path: str | path, compress?: bool}`
- `XOpts` = `{overwrite?: bool, skipExisting?: bool, preservePermissions?: bool, stripComponents?: int, pattern?: str | path, maxBytes?: int}`
- `EOpts` = `{overwrite?: bool, skipExisting?: bool, preservePermissions?: bool, mkdirs?: bool, maxBytes?: int}`
- `Cookie` = `{name: str, value: str, domain: str, path: str, hostOnly: bool, secure: bool, httpOnly: bool, sameSite: str, expires: int | float | null, lastAccess: int | float, quoted: bool}`
- `Req` = `{url: str, timeout?: int, followRedirects?: bool, headers?: {str: str | int | path}, body?: str | int | path, cookieJar?: [Cookie]}`
- `Resp` = `{status: int, reason: str, headers: {str: [str]}, body: bytes, cookieJar?: [Cookie]}`

"Path-like" below means the runtime calls `CastString`, which accepts str, path, int, and a bare word inside a list literal.
Following the seed (`readFile`), path-like arguments are written `str | path`; see "Unsure" item 3.

## Builtins in the runtime but missing from `BuiltInList.go`

Method: every `case "..."` label at the top level of the LITERAL switch in `evaluateBuiltinToken` (Evaluator.go 5939 to 12325), compared with the keys of `BuiltInList`.
Nested `case` labels inside that function were also checked; all of them are in the list.

- `and` (11476, shared case with `or`)
- `or` (11476)
- `~` (6896): pushes the home directory as a `str` (not a `path`), via `evalTildeToken`. Words starting with `~/` are handled in the switch's `default` (also `str`), so they are not fixed names.

In the other direction, `return` is in `BuiltInList` but has no case in that switch; it is handled in `processTokenToken` (1746). That is correct, not a gap.
`wln` is in neither the runtime nor `BuiltInList`, but is in both checker tables (see above).

## Runtime behavior that looks like a bug

1. `e`/`ec`/`es` (8098) set `StderrBehavior` without checking `StderrDestinationDesc`, which `^` does (11651). So `[cmd] 2> f e` or `[cmd] 2>&1 e` gives stderr two destinations, and `[cmd] ^ e` silently replaces the capture, against "Each stream has exactly one destination". Their messages also say "Cannot set stdout behavior" for a bad operand, and "set stderr behavior to lines" on an empty stack for all three.
2. `wln` is in the old and seed checker tables but not in the runtime (see the table).
3. Every path-like argument (archives, `readFile`, ...) goes through `CastString`, which accepts `int`: `5 zipList` lists an archive named `5`. Probably unintended.
4. `httpPost` cannot send a binary body: `body` goes through `CastString`, which rejects bytes. Documented as "stringable", so this is a limitation rather than a bug.
5. `completionDefs` quotes run a completion def's body with the caller's variable map, not as a def call, so variables the def stores leak into the caller's scope. I did not trace what `return` inside such a body does when run through `x`.
6. `stringOption` (`pattern`) says "must be a string/path" but also accepts int (CastString).

## Unsure, or needs a decision

1. **Read-only list parameters.** `zipPack`/`tarPack` only read their list. Under invariance a stored `[str]`, `[path]`, or the `[str | path | {path: path, archivePath: str, mode: int}]` that `tests/success/zip_pack.msh` and `tar_pack.msh` store in a variable does not fit `Pack`. Per-type overloads (`[str]`, `[path]`, `[shape]`) beside the union one do not help: a fresh `["a" "b"]` then fits both `[str]` and `Pack`, and `choose` reports an ambiguity when no argument is unsolved. Using only the three homogeneous overloads loses mixed lists. The design gives read-only dict builtins `{}` (rule 3); the list analogue (a covariant, read-only list parameter for builtins that neither write nor keep the list) is not in the signature syntax. I kept the single union candidate.
2. **Option dicts that hold a shared container.** Verified in a scratch copy of the repo: `[] jar! {url: "x", cookieJar: @jar} httpGet` is rejected, and so is `def f ([Cookie] -- ) jar! {url: "x", timeout: 3, followRedirects: true, body: "", cookieJar: @jar} httpGet drop end`. The literal is not fresh because it holds `@jar`, so S2 rejects every missing optional key (`timeout?`, `headers?`, ...), and an optional field with a union type (`body?: str | int | path`) needs a value of exactly that union (S2 requires `≡` because the target field is writable). The documented cookie-jar pattern (`doc/mshell.md`, "Cookie jars") therefore never type-checks, and neither does a request with `headers: @h`. Literals with only immutable values (`{url: @u, body: 5}`) are fine. The fix is the same as item 1: a read-only parameter view, where optional fields accept a missing key and field types are compared with `≤`. The `cookieJar` field stays invariant inside it, because the builtin writes the jar. The design's "top-fresh" refinement would also cover it. Narrowing `body?` and `headers?` to `str` alone does not fix it.
3. **`CastString` accepts int.** Rule 1 says to add it, but the seed writes `readFile` as `str | path`. I followed the seed for path-like arguments and kept `int` for `body` and header values, where an int is a natural value (and the old sig had it). Whichever way is chosen should be applied to every CastString builtin.
4. **Output shapes are open.** `zipList`/`tarList`/`httpGet` outputs are written as open shapes because the signature syntax has no exact shape. That is sound but less precise. For example, a fresh `zipList` result cannot be retyped to add an optional key.
5. **`dbg`.** I registered `( -- )`. Whether the core should also print its type stack there is a feature decision.
6. **`keeps` on httpGet/httpPost.** I think it is sound by the dead-request argument above, but the formal model has no builtin that returns part of a consumed fresh input inside a new wrapper. Dropping the mark (shared output) is always safe.
