## Notes on overloads (rule 6)

- With a known argument, no two candidates fit at once.
- An empty literal `[]` (type `[T0]`) fits every per-element-type candidate of `sort`, `sortV`, `uniq`, `sum`, `max` and `min`.
  The checker reports "ambiguous typing" (verified: `[] sort drop`, `[] sum drop`).
  The runtime fails on `[] sum`/`max`/`min` anyway, but `[] sort` and `[] uniq` are valid there.
- Union-element overloads (`[int | str]`, ...) were rejected for the same reason.
  A fresh `[1 2]` is ⊑ `[int | str]` by Retype, so it would fit two candidates.

## Runtime behavior that looks like a bug

1. `and`/`or` with a quote: `obj2.(MShellBool)` is an unchecked type assertion (lines 11502 and 11528).
   `5 (true) and` panics the Go runtime instead of giving an error (confirmed with a scratch build).
2. `and`/`or` with a quote: after the quote runs, the stack top is popped before `ShouldPassResultUpStack` is checked.
   So a `break`/`continue` inside the quote removes one value from the loop's stack, or fails with "the stack was empty".
3. `sortVu`: dead code at 8212 (`t.Lexeme == "sortVu"`); no such builtin exists.
   The old table registers it.
4. `map` on a grid: rows after the first that are neither GridRow nor dict are silently skipped, leaving nil cells (the type switch has no default).
   Dict rows with keys the first row lacks lose them silently; missing keys give nil cells.
5. Grid `map`/`filter` and `sortByCmp` comparators pop only the top and ignore anything left below.
   The list `map`/`filter` demand exactly one value. The behavior is inconsistent, not unsound.
6. `nth` on a quotation returns a one-token quotation, and on a pipe returns the command.
   This looks accidental (generic `Index` methods).
7. `sort`/`sortV` turn an `[int]` into a `[str]` sorted lexically (`[10 9] sort` is `["10" "9"]`).
   This is documented in `doc/mshell.md`, but surprising.
8. `uniq` docs say "Works for all non-compound types", but bool, bytes, null and Maybe elements fail.

## Things I was unsure of

1. **`maybe` and `⊥`.** With `(Maybe[a] a -- a)`, the core checker rejects `none 5 maybe`: `'maybe' expected <bottom> at argument 1, got int`.
   It solves `a = ⊥` from `Maybe[⊥]` (structured inputs first) and then checks `5 ≤ ⊥`.
   It also rejects `5 just "x" maybe`, which the runtime accepts.
   The first looks like a checker issue: a `⊥` from `none` should probably not fix a generic, or the generic should be the join of the Maybe content and the default, as `joinRepeated` does for bare inputs.
   The design rules out the old `t | u`. Please decide.
2. **`extend` keeps.** The receiver is fresh after `extend` only if the consumed top list is treated as dead, since it still points at the moved elements.
   That is the argument `Slice.v` proves for `take`/`skip` (`inv_slice_dp`), not one proved for `extend`.
   If it should not rely on that, drop `extend` from the keeps loop (its output becomes shared, which is always safe).
3. **`CastString` inputs.** Rule 1 adds `int` (and `path`) to `strCmp`, `versionSortCmp`, `index` and `lastIndexOf`, which accept them through `CastString`.
   For `sortBy` I wrote only `str | [str]`: `[int]`/`[path]` column-name lists are also accepted at runtime but would need extra overloads, and a column named "1" from an int seems unintended.
   Should these `CastString` widenings be in the table, or is `CastString` accepting int a runtime looseness to keep out of the types?
4. **Dict forms of `map`/`filter`.** I described the Get-Key reading (rule 3), but did not decide whether a shape input to `map` should keep its labels.
   For `filter` it cannot, because required labels may be removed.
5. **Design doc text** that disagrees with the runtime: "Only `setd` and `del` need `{str: T}`" (there is no dict `del`).
   `pop` is listed as returning the same list, and `sortBy` as a list word.
   `sortByCmp` (in place, shared) is the list sort with a quote, and it must not get the new-list mark.
